# 0.7.0 — complete action binding and isolated MCP grants

Requires Tenuo Python SDK 0.3.6 or later in the 0.3 series. The default authorizer is pinned to 0.3.6. Claude Code plugin version: 0.2.0; GitHub policy pack version: 5.

## Changes

- Approval signatures bind the complete tool invocation, including arguments that policy does not constrain. An approval for one pull request cannot authorize another pull request merely because both use the same owner and repository.
- MCP grants include the configured server identity (`mcp__github__merge_pull_request`, for example). Native tools and different MCP servers cannot share grants accidentally.
- Approval-gated MCP actions fail closed in local mode and when a Cloud approval policy is missing, including actions with concrete argument constraints.
- Managed hooks use an explicitly validated administrator-owned Python virtualenv with isolated startup. Import or startup failures deny the call.
- The MCP proxy reloads policy for each call. Invalid policy denies; downstream, server identity, or transport changes require reconnecting.
- Policy parsing, constraints, routing, action identity, Cloud compilation, and MCP transport now live in separate modules. Existing CLI interfaces remain available.
- Raise MCP, certifi, AnyIO, and PyJWT minimum versions to exclude the vulnerable versions reported by repository dependency advisories.
- Runtime dependencies are defined in pyproject.toml; requirements.txt installs that project. Source archives include the plugin and its tests. Publishing checks the release tag, package version, and regression suite before building artifacts.

## Upgrade from 0.6.x

1. Install `tenuo-claude-code==0.7.0` in the environment used by your hooks and proxy, then run `tenuo-claude install-authorizer` for the 0.3.6 native authorizer. For Docker deployments, remove an older explicit image override or update it to `tenuo/authorizer:0.3.6`.
2. Set `mcp.server` to the exact server name in the client's MCP configuration. Existing generated proxies default to `tenuo-files`; a server registered as `github` needs `mcp.server: github`. One policy governs one server identity. Server names must not start or end with `_`, tool names must not start with `_`, and neither may contain `__`. Ambiguous incoming names are denied even when an older policy would allow them; rename these servers/tools before upgrading.
3. Recompile policy and remint warrants with `tenuo-claude refresh`. Cloud deployments must first run `tenuo-admin setup` to update their warrant configuration and approval policies, then refresh. Old warrants do not carry the new namespaced capabilities or complete-request constraint.
4. Restart the authorizer with `tenuo-claude down` followed by `tenuo-claude up`, then reconnect MCP clients so they load the upgraded proxy. Run `tenuo-claude verify` before resuming work.
5. For managed deployments, install the package and dependencies into a root-owned virtualenv whose files and ancestor directories are not group/world-writable. Regenerate templates with `tenuo-claude managed-template --platform linux --hook-python /opt/tenuo/venv/bin/python` (or `--platform macos`), and deploy them through your administrator. `--bin` is no longer accepted as a managed trust boundary. Use a non-editable installation without system-site inheritance or executable `.pth` startup hooks; plain `.pth` paths must remain inside the validated virtualenv. Create the environment with `python3 -m venv --without-pip /opt/tenuo/venv`, then install the package with `uv pip install --python /opt/tenuo/venv/bin/python tenuo-claude-code==0.7.0`, as the administrator.

The reserved `__tenuo_request` field contains canonical JSON for the original tool name and all arguments. Do not use it as a policy constraint or exemption. Approval metadata includes the full request for review; consumers must allow that additional field. Pending approvals from an older version must be requested again.

Tenuo 0.3.6 also supports opt-in single-use approvals. This adapter does not enable that feature: complete-request binding prevents approval reuse for a different action, but does not itself prevent repeating the identical approved action within the approval's validity period.

Upstream: [Tenuo 0.3.6](https://github.com/tenuo-ai/tenuo/releases/tag/v0.3.6).

## Release validation

- 479 regression tests passed with the frozen dependency set and again from the installed source archive with freshly resolved dependencies.
- Built and installed both wheel and source distribution; CLI version and bundled policy packs verified.
- Tenuo authorizer 0.3.6+authz.3 on macOS: 13 bootstrap probes and 24 deep enforcement probes passed. Additional live calls verified MCP server isolation, path constraints, native reads, and policy-file protection.
- Marketplace and plugin manifests passed `claude plugin validate --strict`.

Cloud approval lifecycle integration and live Claude Code hook execution were not exercised in this validation; request hashing, approval compilation, hook contracts, and MCP subprocess behavior are covered by automated tests.
